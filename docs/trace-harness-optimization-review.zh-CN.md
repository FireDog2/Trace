# Trace Harness 优化评审：结合岗位 JD 与 ProData 的取舍建议

评审日期：2026-10-28。本文用于选择后续工作，没有实施下述业务改造。

依据包括用户提供的 JD 调研报告、Trace 当前工作区代码（含尚未提交的融合修改）、ProData 的说明文档及相关实现。JD 中的公司、日期和招聘数量沿用报告，不作为本次独立核实的招聘事实。文档中的建议、命令和简历表述均作为待分析内容处理。

**我的判断：Trace 最值得增加的是“能测量效果、验证结论、保持分析状态并可靠续跑”的能力。** 现有 SQL 治理、角色白名单、审批、Trace 和上下文投影已有基础；继续增加工具数量或框架名称，收益可能低于把这些能力做成可量化的闭环。

ProData 与 Trace 可以形成清楚的分工：ProData 提供模型训练、过程评分和经验迭代的研究基础；Trace 展示这些模型在受控业务环境中的执行质量、恢复能力和资源效率。两者通过任务集、动作协议、评测结果和版本记录连接。

## 1. 当前已经具备什么，哪些还不能算完成

| 方面 | 从代码确认的现状 | 评审判断 |
| --- | --- | --- |
| 工具与权限 | 类型化工具、角色白名单、项目范围检查；PostgreSQL 有 AST、字段策略、只读事务、一次性审批和查询预算 | 是现有亮点，优先保留和回归验证 |
| 多 Agent | Knowledge / SQL / Report 分工；线程池、worker claim、持久轮次和截止时间、取消检查 | 已有有界协作，不需要为了 JD 再增加一套多 Agent 框架 |
| Context | 完整消息持久化、有界投影、Checkpoint、工具结果压缩、超长后重试 | 具备压缩机制，但长程语义保留和真实 token 预算仍需加强 |
| 恢复 | 审批后恢复、失败任务重试、teammate 的失败分类和重试检查 | 不等同于任意崩溃点恢复；启动时会把遗留活跃 teammate 标为失败 |
| Trace / Replay | 脱敏事件、父子关联、产物引用、事件序列检查、只读回放包 | 适合审计；尚不是可用于重执行和实验对比的环境快照 |
| 报告证据 | 检查引用 Artifact 存在、属于同项目，记录引用关系 | 验证的是引用有效性，尚未验证具体结论是否由证据支持 |
| 本地模型融合 | `LocalTransformersProvider`、进程内缓存、互斥锁、JSON 动作解析、可选依赖 | 代码适配已接入；不能据此声称 Trace 模型已训练或端到端验证 |
| Skill | 成功轨迹候选及显式请求的失败复盘；Curator 无工具；批准后仍禁用 | 审核边界清楚，但经验尚未进入受控实验与效果验证闭环 |
| 工程验证 | 单元、组件和脚本化验收测试较多，有 PostgreSQL 集成测试代码 | 工程回归基础较好；未看到完整的真实模型任务级评测与消融管线 |

本地模型测试目前主要验证解析器、错误拒绝和对象构造，没有执行真实 checkpoint 的生成、并发、显存和取消验证。本次也没有运行训练或下载模型。

## 2. 先处理的三处具体问题

这些问题由当前源码的隔离探针复现。探针从源文件抽取实际函数，用内存对象替代数据库、Provider 和文件写入；结果是局部行为证据，不代表完整服务集成测试。

| 问题 | 复现结果与原因 | 建议修正 |
| --- | --- | --- |
| 摘要可能不吸收新信息 | `context.py:369` 的 `_summarize` 先拼旧摘要，再追加新消息，最后截前缀。旧摘要达到 12,000 字符时，新增指标口径没有进入结果 | 用结构化状态合并和每类字段预算；至少确保新事实、用户修正和下一步动作有独立保留空间 |
| 报告的证据门槛依赖英文标题 | `reporting.py:36` 只在出现精确的 `## Key Findings` 时要求至少一个引用。中文“关键发现”无引用也被接受；同项目无关 Artifact 也可以通过当前引用检查 | 将证据要求绑定报告类型及结构化结论，不依赖标题文本；分开校验“引用有效”和“结论得到支持” |
| Lead 的重试预算没有成为执行前硬限制 | `agent.py` 在执行后记录 recovery。设预算为 2，使用 A→B→A→B→A 的失败调用序列，A 实际执行 3 次；连续相同调用检查挡不住交替调用 | 与 teammate 一样在执行前检查 `recovery.exhausted(signature)`；后续再持久化预算，覆盖暂停与重启 |

第三项不表示可以无限执行：总工具动作上限仍存在。它说明“每种失败调用只执行预算内次数”这一层约束尚未完全落实。

建议先把这三项作为一个小修订包，预计约 1–3 个开发日，包含针对性的回归验证。报告语义验证的完整实现另计。

## 4. A：从“工程测试通过”走到“Agent 效果可测量”

**当前缺口。** `ScriptedProvider` 能验证工程分支，但不会检验真实模型能否选对工具、理解口径并生成正确结论。Golden Trace 也不能直接充当真实模型评测结果。`AgentRunner._complete_task` 推进运行状态，没有答案真值校验，因此 `completed` 不能直接统计成“分析正确”。

**最小实现。** 新增独立的 `evaluation/`，以真实 `AgentRunner` / `ToolRegistry` 为被测对象。每个任务记录固定数据、问题、成功条件、允许的人工输入、资源预算和评分器；每次 trial 使用独立数据库与工作区。

第一版可设计约 30–50 个任务，覆盖数值与口径、跨表分析、多轮修正、故障恢复、审批与越权。先采用可控制的小数据和独立参考计算，再用 ProData 的公开数据分析任务补充。LongDS 可作为长程扩展来源；若改了题目或裁剪对话，应明确报告为适配任务集，不能冒充原基准成绩。

评分分开呈现：答案正确率、重要结论的证据支持率、有效工具动作率、恢复率、审批等待是否正确、越权是否被执行、token、端到端耗时与人工等待时间。模型提出越权动作和执行器实际放行越权应分别计数。

**核心实验。** 固定模型和数据，对比当前 Harness 与改进 Harness；然后再固定 Harness 比较基座模型、SFT、SFT+RL。对候选方案做配对任务比较及少量重复试验，保留原始 trial、失败类别和资源消耗。不要用“多次重试取最好”替代单次成功率；小样本的小幅提升也应报告不确定性。

Anthropic 的官方评测说明明确区分任务、trial、轨迹、环境最终结果和评分器，并将“Agent”视为模型与 Harness 的组合。这支持把工程回归与任务效果评测并行建设。[官方说明](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

**验收产物。** 一个可重复执行的离线入口、一份冻结任务集、一份按任务比较的结果表，以及能回到 Trace 的失败列表。改善某一指标时必须同时检查正确性、安全和成本是否退化。

## 5. B：验证“这条结论是否真的成立”

**当前缺口。** `ReportService.publish` 的引用检查不能发现“引用真实表格，但同比基期错了”“净收入忘记扣退款”“Join 后行数膨胀”等静默分析错误。

**建议先做确定性 Verifier 服务。** 不必马上增加一个独立 Agent。将报告中的重要结论表示为结构化 Claim，例如：指标、值、单位、时间范围、筛选条件、分组、输入 Artifact、参考计算及误差容忍度。验证器读取冻结的证据，对可计算项独立复算；对无法确定的开放式判断返回 `unverified`，避免把模型打分当真值。

可以从三类检查开始：数值与单位一致；口径和时间范围一致；聚合、Join 基数及总分项一致。检查器和被检查的报告不得共享同一个未经验证的计算结果作为“答案”。

将结果写成 `verified / failed / unverified`，同时保存原因和证据定位。失败后给执行者最多 1–2 轮修正机会；修正仍失败就保留明确的不确定项或交由用户处理。有限次修正需要纳入任务预算。

**验收方式。** 制作含已知错误的报告与正确对照，测量错误检出率、错误放行率、正确结论误拒率和额外延迟，不能只展示几条成功拦截案例。

**与 ProData 的关系。** 可借鉴 DataCOPE supervised verifier 的真值对照方式，并把 Trace 的验证结果转为离线训练标签。DataPRM 更适合先做离线补充评分：只有当确定性规则抓不到关键静默错误，并验证过评分与人工判断的一致性后，再决定是否纳入在线流程。它不替代权限网关。

## 6. C：让压缩后保留下来的是“分析状态”

**当前缺口。** 当前 Checkpoint 是按消息顺序摘取和截断的文本；反复把旧摘要放在新信息之前，容易让历史占据预算。token 估计采用字符数近似，本地 Provider 还会额外拼接 JSON 协议和工具描述，预算应以最终编码请求为准。

**最小实现。** 在完整 Transcript 之外维护版本化 `AnalysisState`，包含当前目标、指标定义、时间与筛选条件、已确认事实、被推翻的假设、有效 Artifact、待解决问题、计划位置和下一步动作。用户修正应覆盖相应字段，并记录来源消息与旧版本；不要把模型猜测自动写入已确认事实。

新摘要应由“上一版状态 + 新事件”合并产生，按字段分配预算。保留原始消息作为审计来源，压缩后的状态可追溯到对应消息。对较大结果采用“摘要 + Artifact ID + 按需读取”，减少反复向模型塞原始行。

本地推理按 tokenizer 与 chat template 计算最终输入长度，预留生成 token 和协议余量；超出硬限制时应确定性裁剪或返回可恢复错误。其他 Provider 保留带余量的估计，并区分估计值与实际 usage。

**验收方式。** 连续多次压缩后，修改指标定义、回滚筛选、切换分析分支，检查新口径是否生效、旧结论是否失效、工具消息协议是否完整。报告答案质量和 token 成本两个维度。

ProData 的 LongDS 已明确覆盖状态继承、更新、反事实、回滚和多状态组合，适合用来设计这类任务；不需要把 ProData 的 Agent Runtime 整体搬入 Trace。

## 7. D：从“知道失败了”走到“知道从哪里继续”

**当前缺口。** teammate 已有持久轮次、截止时间及 worker claim，审批恢复也能重建暂停的调用。但 `mark_interrupted_runs` 会把遗留 created / working / waiting 标为失败；Lead 的动作计数与 recovery 状态在 `run()` 内重新创建。已有历史消息不等于工具动作有可恢复的提交记录。

**最小实现。** 为工具动作增加持久账本，保存逻辑动作 ID、attempt、输入摘要、状态、产物和提交点。区分“未开始”“执行中但结果未知”“结果已提交”。模型请求可以重试；创建文件、发布报告和消费审批等动作需要检查既有提交结果。

进程恢复时，从最后已提交动作继续；恢复预算与截止时间，不因重启刷新额度。审批仍要按原范围和策略版本验证，不能把历史批准当成永久授权。对执行结果不明的动作，先核对文件和账本，必要时暂停处理。

优先覆盖四个断点：执行前崩溃、文件已写但注册未完成、产物已注册但工具消息未保存、审批批准但尚未执行。复用 PostgreSQL 已有 attempt 和预算机制，逐步统一，不重写数据库安全网关。

**验收方式。** 在这些边界注入进程故障，验证恢复位置、重复产物数、审批消费次数、预算连续性及终态一致性。目标是可恢复且避免重复副作用；跨数据库和文件系统不能仅凭一张账本就承诺严格 exactly-once。

长程 Agent 的官方实践也强调，压缩之外还需要清楚的进展记录和可接续的工作产物；这可作为设计参考。[官方说明](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)

## 8. E：把本地模型适配补成可管理的推理运行时

**当前缺口。** 本地模型已通过进程级缓存避免重复加载，并使用 `threading.Lock` 串行生成。但锁没有队列容量、等待时限或取消接口；`generate()` 未接入任务截止时间。多个 Agent 的执行线程存在，并不代表模型推理能并发或高效批处理。

`ModelResponse` 目前也没有 usage、finish reason 和模型版本字段，云端返回的 usage 没有传入统一响应。因此还不能直接依赖现有 Trace 统计完整 token 成本或区分排队与生成耗时。

**最小实现。** 保持既定的进程内推理方案，增加有界队列、超时入队、排队取消和生成阶段的协作式停止；任务取消后丢弃迟到结果，避免继续触发工具。记录排队耗时、输入/输出 token、模型及 tokenizer 版本、结束原因和资源错误类别。

统一 Lead、teammate 和重试的任务预算，至少包含总 token、墙钟、工具动作和 SQL 次数。墙钟需明确人工等待是否计入。CUDA 生成的停止有实际边界，需测量取消响应时间；若必须强制终止推理，应单独评估进程隔离，不能承诺线程一定可抢占 GPU。

**验收方式。** 用同一 checkpoint 对比单任务、多个 teammate、多个任务同时提交时的吞吐、P50/P95 延迟、队列拒绝率和取消延迟，并检查质量是否变化。没有测量到瓶颈前，不必引入独立 vLLM 服务、Kubernetes 或分布式调度。

## 9. F：执行隔离与针对 Harness 的对抗回归

**当前缺口。** `PythonExecutor` 使用 AST 检查、`python -I` 子进程、超时和执行后的文件检查；`SECURITY.md` 已明确它不是 hostile-code sandbox。工作目录、环境清理和事后恢复不能替代操作系统级读写与网络隔离。

**最小实现。** 定义执行器接口，保留可信本地执行模式，另提供隔离后端：只挂载任务所需输入并设只读；使用独立输出目录、禁网、内存/CPU/进程数/磁盘限额和受限身份；运行结束仅导入声明的产物。Windows 下应先确认 Docker Desktop 或 WSL2 条件，再决定具体实现。

对抗集围绕真实入口构造：数据单元格或知识文档中的指令、伪造 teammate 交接、跨项目 Artifact、引用无关证据、间接文件访问和失效审批。分别测量攻击是否引发危险执行，以及正常任务被误拦的比例。隔离执行不负责解决所有语义注入问题，权限和证据校验仍需独立存在。

**与 ProData 的关系。** 其 `async_interpreter.py` 有 conda 子进程、超时和 RLIMIT_AS，也有缺包自动安装与 Linux 路径假设。这些是训练执行经验，不能原样充当 Trace 的安全沙箱，更不应自动把动态安装能力开放给线上模型。

## 10. G：先测 Skill 是否有效，再讨论启用

**当前缺口。** 失败复盘已融合，但 `_workflow_evidence` 主要提供前 100 条事件的类型、状态、工具和产物数量。长轨迹的关键失败可能在后面，Curator 获得的计算语义也有限。当前静态校验和人工批准不能证明一条 Skill 会改善任务效果。

**最小实现。** 保持候选默认禁用，先允许在独立离线实验里选择候选。提取失败前后的关键片段及经过审核的脱敏口径、错误假设、修正方法和可计算证据；按任务类别选择，避免把全部经验塞进上下文。

用相同模型、数据和预算比较无 Skill / 人写 Skill / 候选 Skill。保存适用范围、来源任务、版本、效果和退化任务；只有留出集有收益且通过回归的候选，才值得另行设计显式启用和回滚流程。本次建议不等于授权改变现有启用策略。

训练集与 Skill 提炼集应和留出集按项目、数据来源或任务模板分组，不能只随机切分同一任务的多条 rollout。避免把具体题目答案写进经验后再宣称泛化提升。

## 11. H：让计划能够驱动执行与 Replan

**当前缺口。** 计划有 revision、step title 和 status，但主要是顺序步骤记录；还缺少明确的依赖、输入输出、验收条件及失效传播。模型修改计划文本不等于运行时完成动态调度。

**最小实现。** 先为步骤增加 `depends_on`、输入 Artifact、输出类型、完成条件和失败策略。让工具结果更新步骤状态，在缺列、口径变更、数据不足、审批拒绝等明确事件发生时重新规划受影响部分。限制重规划次数，并继承预算。

不必先做通用 DAG 平台或增加 Agent 数量。验证“上游数据变更后，只重算受影响的结论”“已有有效产物可复用”“审批拒绝后不会换路径绕过”即可形成有价值的最小版本。

## 12. Trace 与 ProData 的衔接建议

训练侧暂不需要复制一套算法清单。优先完成四个连接点：

1. **动作协议一致。** Trace 使用结构化工具动作，ProData 原有代码标签/解释器轨迹不能直接等同于 Trace 样本；本地 JSON 协议、角色工具列表和工具返回需要一同版本化。
2. **共享评测定义。** 先用 A 和 B 明确任务成功与可验证结果，再把其中部分验证结果用于 RL；训练 reward 与最终留出评测应有独立检查，避免只优化评分器漏洞。
3. **环境语义一致。** rollout 使用隔离数据和审批模拟器，覆盖等待、拒绝、失败与恢复；不可直接消费真实审批或操作用户产物。尽量复用工具的纯计算和校验逻辑，减少训练与线上结果形状不一致。
4. **模型与 Harness 分开归因。** 设计“基线模型 / 训练后模型 × 当前 Harness / 改进 Harness”的对照。登记模型、数据、动作协议、工具策略、提示及评分器版本，回答收益究竟来自哪一侧。

DataPRM 的主动执行验证、DataCOPE 的轨迹筛选及 LongDS 的状态演化任务值得复用；它们分别对应评分、经验实验和长程评测，不需要整体替换 Trace 的 Runtime。

## 13. 选择顺序与暂缓项

| 你的主要目标 | 推荐选择 | 可以展示的具体证据 |
| --- | --- | --- |
| Agent 算法 + Harness 综合能力 | 小修订包 → A → B → C | 相同模型下，结论错误、状态丢失和成本如何变化 |
| Harness / Infra / 系统侧 | 小修订包 → A → D → E | 崩溃恢复位置、重复副作用、预算、排队与取消数据 |
| Agent 评测 / 安全方向 | 小修订包 → A → B → F | 错误检出、错误放行、攻击成功和正常任务误拒 |
| 与 ProData 自进化路线呼应 | 小修订包 → A → C → G | 经验在独立任务上的净收益与退化情况 |

建议暂缓：为 JD 单独加入 Kubernetes；再包装 LangGraph / AutoGen；没有测量依据的全向量记忆；增加更多 Agent 角色；直接自动启用 Skill；重复搭建第二套 RL 主干；完整重做 SaaS 登录与租户系统。它们各有适用条件，但当前不是最突出的能力缺口。

项目成果应写已经测出的变化，例如“相同模型下，错误结论放行率从 X 降为 Y，成本变化为 Z”。在评测完成之前保留 X/Y/Z，不预先写提升百分比，也不把已有 ProData 文档里的成绩当作当前 Trace 的成绩。

## 15. 工作流程专题的后续修订

结合用户对交接 Schema、确定性校验、修正上限与部分完成工作量的核对，补充了 [开源实现调研与分阶段方案](trace-workflow-reference-design.zh-CN.md)。工作流程专题采用“结构化交接 → 结束前验收 → 完整任务约定”的顺序，事件唤醒和任务分级后置；该顺序用于流程改造，和上文针对项目整体能力的 A–H 清单属于不同层级。
