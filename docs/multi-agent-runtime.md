# Multi-agent runtime

The lead coordinates at most three active teammates: Knowledge, SQL, and Report. Role allowlists prevent a Knowledge teammate from calling SQL tools and constrain every teammate to its task. Runs are durable (`created`, `working`, `waiting`, terminal), independently message-scoped, cancellable, and have bounded turns/deadlines. Each row persists the parent analysis trace and spawn event so a fresh worker can resume correlation after restart.

SQL Agent also has `run_python` for CSV/Excel and Python/Pandas analysis. Report keeps its existing Python permission; Knowledge and Curator do not gain it. Python defaults to a dedicated, resource-limited, network-disabled Docker environment with no host fallback. See [Python execution](python-execution.md) for image setup, input snapshots, dataset lineage, limits, and the explicit trusted-local mode's security limitations.

New business teammates use version 1 role-specific Pydantic handoffs. The same Pydantic model generates the prompt JSON Schema and parses the result. Knowledge returns versioned definitions, SQL returns query artifact IDs, and Report returns its report, charts, and evidence IDs. A teammate's execution may complete with a `ready`, `partial`, or `blocked` handoff; these are subtask outcomes, not new parent-task states. Curator keeps its separate Markdown protocol.

`spawn_teammate` also accepts `input_artifact_ids`, `knowledge_refs`, `expected_output_kind`, and `plan_step_id`. Omitted artifact inputs snapshot project source datasets and successfully produced current-task outputs; an explicit empty list supplies no artifact inputs. The application stores the work order, content hashes, and validated knowledge versions. Explicit historical inputs remain possible within the project, but failed executions and changed recorded evidence are rejected. A plan-step reference must belong to the latest plan for this task.

DuckDB results, including empty and small results, are always materialized with schema and bounded row/byte limits. Tool execution records the producing task, teammate, execution, and content digest. Handoff checks enforce artifact type, producer, snapshot, lineage, knowledge scope/version, and report evidence links. Receipts are application-owned and describe **reference validation**, not numerical or semantic correctness. API and replay expose receipts; historical results retain their original JSON and are marked `legacy_unvalidated`.

Malformed handoffs have at most one persisted format-repair attempt. The repair request advertises zero tools, and any returned tool calls are rejected before execution. Evidence validation failures terminate safely without inviting the model to fabricate a replacement reference. The original Lead delegation, role permissions, approval replay, and parent-task completion behavior remain in place; task-level delivery acceptance is separate future work.

The manager claims worker leases to avoid duplicate execution and marks stale active work interrupted at startup. Shutdown requests cancellation and does not promise immediate process termination. A fourth role, `CURATOR`, is not available to the lead: only the accepted-run path may create it, one per trace, and its tool allowlist is empty. The design is bounded delegation, not an unrestricted swarm.

Frontend passed all 49 tests and the production build. Ruff, mypy, and Prettier checks passed. Contract tests exercise real Knowledge/SQL/Report tool paths, forged and stale evidence, input snapshots, repair isolation and persisted budgets, and migration rollback/legacy compatibility. These checks use deterministic model providers; they do not establish a trained model's task quality or a live PostgreSQL deployment's behavior.
